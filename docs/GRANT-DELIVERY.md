# Weekly grant delivery, local candidate, September 29, 2026

This implementation is not installed, enabled, or proven in production. No provider requests, signup confirmations, campaigns, emails, secrets, account changes or scheduler changes were made while preparing it.

## Data and matching

The website adds `/api/public/grant-inventory`, containing exactly its existing public projection, inventory-verification date, and SHA256 of the projected JSON. Held/raw records never enter this feed. The live runner always retrieves the fixed canonical HTTPS address with redirects disabled and no cache, validates its digest, and stops if the verification date is older than eight days. Installed frontend source is used only for offline fixtures. Before each send it fetches the feed again and requires the exact same data.

Every enabled Monday (Pacific time) weekly run observes the public snapshot into `publication-ledger.json` in the same private journal directory. Before signup admits users, an explicit one-time initializer establishes a silent baseline of already-active IDs using the actual launch-time feed and timestamp on any Pacific day. It creates no alert receipts, makes no Mailchimp requests and refuses an existing ledger. Scheduled runs require this baseline and never initialize it implicitly; they send no historical inventory. Later new IDs or watchlist-to-active transitions receive their actual first observed active date, plus snapshot digest, feed reference, and observation timestamps. This is not represented as the historical publication date. Ordinary updates or reopening the same ID never generate another alert. A genuinely new funding cycle needs a new canonical record ID. An official-call URL change for an observed cycle stops processing for reconciliation.

Only confirmed `subscribed` contacts with `IHEGRANTS=YES` qualify. Pulse selection is independent. Criteria are ANDed across categories and ORed within each category; unknown/invalid saved criteria fail closed. Amount matching uses explicit per-award USD, never the program pool. Institution-only grants cannot match an unverified institution. No match means no campaign or email. Closed/expired/held/watchlist calls are not sent.

Dates use Pacific calendar days. Scheduled observation and matching use the current Monday-to-Monday window, including the actual observation date. There is no fabricated backfill. Signup-day listings are excluded. The ledger retains every previously public ID. For a genuinely new public ID whose valid portal-added date falls after the prior observation day and no later than the current observation, signup ordering uses that actual addition date: the signup Pacific day must be strictly earlier. A Tuesday signup therefore receives a new Thursday listing on the following Monday, without another weekly delay. Previously public watchlist activation and unknown/out-of-interval addition dates retain the conservative signup-before-prior-observation cutoff because the precise activation time is unknown. The actual firstObservedActiveDate still determines the current Monday delivery bucket. Weekly observation can miss calls that open and close between runs, consistent with the selected weekly cadence. Ongoing midweek observation is unsupported and rejected before changing the ledger; there is no optional daily/standalone observer. The sole any-day exception is one-time initialization of an absent baseline, which creates no alert-cycle receipts.

## Retry and capacity safety

The journal requires a real, owned 0700 directory and owned, single-link 0600 files. Writes use exclusive temporary creation, fsync, atomic rename and directory fsync. A common atomic lock excludes concurrent journal mutations. Stale locks or pending files require investigation; never remove them and blindly retry a send. The journal stores member hashes, not email addresses, and must remain outside public/static directories and shared backups.

Provider mutation intent is saved before segment/campaign creation or sending. An uncertain creation stops rather than creating a duplicate. A submitted campaign is checked for `sending`/`sent` before another cohort proceeds. An accepted send with a lost response is never blindly resubmitted. Changed consent, data, exact segment members, content or campaign state blocks delivery. Consent and the public snapshot are fetched again before each cohort submission. Cohorts are exact static recipient sets. The runner submits one asynchronous cohort per attempt and reconciles the provider on a later attempt.

Bounds are deliberately fixed at 500 total account contacts and 5,000 account sends, with scheduled use capped conservatively at 4,000 sends in the prior 31 days and 1,000 reserved. These are code safety ceilings based on the earlier account tier, not evidence of today's plan or billing usage. Actual account capacity must be verified before activation. Pending campaigns block overlapping sends. No AI service or paid matching API is used.

## Available host and reversible activation proposal

Read-only local checks found Node 25.4.0 at `/opt/homebrew/Cellar/node/25.4.0/bin/node` and macOS `/bin/launchctl`. No grant-specific LaunchAgent was present in the inspected local LaunchAgents names. The existing frontend is a Vercel deployment; its ephemeral function filesystem is not a valid home for this durable journal. The separate pipeline's tracked Dockerfile uses Node 20 and Cloud Run, so this TypeScript CLI must not be assumed compatible with or durably installed on that service. No cloud scheduler or durable mounted storage was verified.

The smallest no-new-service option is a LaunchAgent on this already-used Mac with a private journal on persistent local storage, invoking the Node CLI from a stable reviewed installation. The Mac must be awake, logged in and connected. Proposed schedule: Monday morning Pacific using --scheduled-drain. This bounded runner retries only known pending/sending states every 30 seconds, up to 600 attempts or six hours, and returns delivery-complete only after all cohorts are confirmed sent. Any uncertain mutation or changed consent/data stops immediately for investigation. Scheduled execution is rejected outside Monday Pacific time, including an unfinished drain that crosses midnight; preserve that journal for explicit recovery rather than silently advancing it. Start the proposed morning schedule early enough for its six-hour bound. Capture its exit status and private logs through the existing operator workflow; completion/failure notification routing remains an activation check.
