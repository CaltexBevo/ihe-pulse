# Email preference capture: staged October 3 release

This candidate combines preference capture with a locally tested weekly grant matching/delivery runner, private retry journal, setup CLI, and public inventory feed. No scheduler is installed or enabled; recurring sending is not operational. See GRANT-DELIVERY.md for the exact activation path and boundaries. Phase 1 publishes the approved signup design with capture closed and the helper text ‘Signups are not open yet’. The live public feed must be available before the one-time baseline. Phase 2 opens capture only after delivery and consent protections are operational and independently verified. No provider calls, account changes, test emails, subscriber emails or production activation occurred during this port.

## Capture behavior

`POST /api/newsletter` retains exact-origin validation, Turnstile action and hostname validation, the 4,096-byte body limit, and the total upstream deadline. New payloads supply `preferences: {pulse:boolean,grants:boolean}` and optional `grantCriteria: {audiences:[],locations:[],areas:[],minimumAwardUsd:null}`. At least one email choice must be true. Supplied criteria must be valid bounded allowlisted values; nonempty criteria are rejected if grants are not selected. Legacy forms without either object remain Pulse-only.

Preference submissions fail closed with HTTP 503 unless `MAILCHIMP_PREFERENCES_SCHEMA=v1`. The flag is an operator assertion that baseline, hosted profile editing, every Pulse sender isolation path, and the operating weekly delivery host are verified, not a live schema or scheduler check. GET /api/newsletter returns only a non-cacheable readiness boolean from the same flag and valid service configuration; it never calls the provider. The shared signup starts disabled, fails closed on an unavailable or malformed GET, and uses the existing helper slot for pending copy. The POST guard remains authoritative. Legacy Pulse forms retain their prior behavior. Do not set it merely to make the UI succeed.

New contacts use a create-only POST with `status: pending` for double opt-in. Existing-contact collisions return the same response as new signups and never update names or choices. No anonymous lookup or update endpoint is added. `/email-preferences` directs existing contacts to Mailchimp's email-verified profile flow; its actual configuration remains an activation check.

Seven fields are defined in `lib/server/mailchimpPreferences.ts`: independent YES/NO dropdowns `IHEPULSE` and `IHEGRANTS`; CSV allowlists `IHEAUD`, `IHELOC`, `IHEAREA`; optional whole-dollar per-award threshold `IHEMIN`; private signup timestamp `IHESTART`. All seven API merge fields must have `public:false` and `required:false`; neither consent dropdown gains a default. API public visibility controls audience-hosted signup exposure and is separate from secure preferences-center selection. In that center, explicitly select only the six optional editable choices (`IHEPULSE`, `IHEGRANTS`, `IHEAUD`, `IHELOC`, `IHEAREA`, `IHEMIN`), preserve blank/no-default choices, and leave `IHESTART` hidden. Criteria text is bounded to 255 bytes per field. Names use the existing FNAME/LNAME fields. Blank criteria mean no filter. The optional grant runner consumes these selections independently of Pulse.
